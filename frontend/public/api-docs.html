Kurukoo Developer Surface

Build on the same OS.

Kurukoo APIs expose canonical identities, requests, capabilities and evidence. They do not bypass conversation, authorization, payment or fulfilment boundaries.

Integration truthAvailability, payment, provider success and delivery remain evidence-gated. Treat every response as current system state, not a promise of external fulfilment.
GET/api/v1/user/profile

Retrieves the current authenticated user's profile and identity context available to the connected client.

Requires authentication. Use the returned identity only for owner-scoped client context.
POST/api/v1/gigs/post

Creates a gig proposal through the canonical opportunity path. The endpoint does not imply acceptance, matching or payment.

A created proposal remains a proposal until the appropriate network and economic evidence exists.
POST/api/chat

Use the canonical conversation surface when the user needs natural-language understanding, clarification, context continuity or action coordination.

Prefer conversation-first entry for user intent. Do not rebuild the routing or governance layer in an integration.
GET/api/chat/economic-requests

Returns owner-scoped Economic Request state for authenticated workspace surfaces and continuation.

Request status is canonical. Clients must render pending, awaiting input and external-dependency states truthfully.
