# FCM external contract and controlled activation notes

The optional FCM adapter is implemented through the existing notification, consent, communication-outbox, delivery-ledger, and Memory Profile owners. It remains **disabled** until a controlled pilot supplies valid Firebase project configuration. This record documents the external activation contract; it neither stores a credential nor represents a planned activation as delivery evidence.

## Verified transport boundary

| Topic | Verified constraint | Kurukoo implementation consequence |
|---|---|---|
| Server authentication | FCM HTTP v1 authorizes a request with a short-lived OAuth token derived from a service account. [1] | The server reads only `FCM_SERVICE_ACCOUNT_JSON`, parses `project_id`, `client_email`, and a private key, mints a short-lived OAuth assertion for `firebase.messaging`, and never sends service-account material to a client. |
| Device ownership | A browser must obtain its own FCM registration before the platform can target it. Web FCM requires HTTPS, a service worker, explicit notification permission, and configured VAPID web credentials. [2] | The authenticated, rate-limited `PUT /api/notifications/fcm-device` registers exactly one validated token for the authenticated owner; `DELETE` removes a matching token. The token is never echoed, exported through the outbox, or placed in a durable outbound payload. |
| Communication consent | Browser permission does not substitute for a user’s consent to external communication. | The same authenticated owner must separately record FCM consent through `PUT /api/notifications/preferences/fcm` with `{ "purpose": "all", "consent": "granted" }`; denied consent suppresses external dispatch while the in-app notification remains available. |
| Acceptance and receipts | A successful FCM HTTP v1 response is provider acceptance, not a synchronous per-device delivery or read receipt. Aggregate reporting is delayed and subject to platform coverage and consent. [3] | The shared ledger may record only `accepted` plus an opaque provider reference. The deterministic in-app notification and its owner-scoped read state remain the immediate receipt signal. |
| Registration freshness | Firebase recommends maintaining registrations with server timestamps, handling client registration changes, and deleting invalid registrations after an invalid response. [4] | The client must upload a current identifier on an intentional permission/registration change. The transport clears an FCM token on a validated `UNREGISTERED` response. A future FID migration must use the same owner-bound registration route, not a parallel token store. |

## Controlled pilot activation sequence

| Step | Operator or client action | Required proof before proceeding | Kurukoo boundary preserved |
|---|---|---|---|
| 1. Establish project | Create/select the approved Firebase project, enable the FCM Registration API where required, and generate or import the project’s public Web Push VAPID key. [2] | The approved project identifier, public VAPID key, and responsible operator are recorded outside source control. | No Firebase key, service-account JSON, registration identifier, or personal data enters Git, templates, logs, or the Admin Control Room. |
| 2. Provision server credentials | Generate a narrowly governed Firebase service-account private key and inject its **entire JSON document** through the deployment secret named `FCM_SERVICE_ACCOUNT_JSON`. Do not use the placeholder value or a filesystem path: the implemented adapter expects raw JSON. [1] | A deployment-secret audit confirms `project_id`, `client_email`, and private-key format load successfully in the target environment; secret values are never pasted into tickets or browser tools. | The existing provider-neutral adapter remains the only sender. Missing or malformed configuration reports `not_configured`/failed; it does not claim delivery. |
| 3. Add the client adapter | On a user-initiated notification-settings action, confirm HTTPS and the existing `/sw.js` service-worker readiness, request browser notification permission, and integrate the FCM SDK through that existing worker registration with the public VAPID key. Do **not** add a competing root `firebase-messaging-sw.js`; any worker-code extension requires a separate PWA-cache/privacy review. Then obtain the current browser registration identifier. The client may handle foreground/background notification display but must not change Kurukoo request, payment, safety, or admin state from a push payload. [2] | A browser-support and permission-denied path shows a quiet unavailable state with no repeated prompt; the normal chat/in-app-notification path remains usable. | No auto-prompt on page load, no device identifier before a user action, no raw conversation content in a notification payload, and no second notification store. |
| 4. Record consent and device | After the user can review the external-notification purpose, call the existing consent route, then upload the current identifier to `PUT /api/notifications/fcm-device`. On opt-out, revoke consent and call `DELETE /api/notifications/fcm-device` with the current identifier. | Real-app checks prove the request is authenticated, owner-bound, rate-limited, malformed identifiers are rejected, and logout/account deletion remove access to private notification data. | Existing consent, Memory Profile, rate-limit, and account-lifecycle owners remain authoritative. |
| 5. Verify bounded send | Use one consenting pilot account and a benign, generic update. Confirm an in-app notification is stored first, then observe only the provider’s acceptance result and opaque reference. | Test evidence distinguishes `accepted` from device display, delivery, engagement, or read. Invalid-registration responses are examined to confirm stale-token cleanup. | The shared outbox and ledger remain authoritative; no direct browser-to-FCM send or fabricated delivery state. |
| 6. Decide on aggregate analytics | If aggregate delivery reporting is needed, obtain explicit data-governance approval and user consent before enabling Firebase Analytics, Data API, or BigQuery export. Reporting is delayed, aggregate, and does not replace Kurukoo’s owner-scoped in-app read state. [3] | A privacy review records data categories, retention, access control, cost ceiling, opt-out, and incident owner. | Programmatic/advertising analytics and notification delivery evidence stay separate; no individual read receipt is inferred. |

> **Do not activate FCM for authentication, payment, escrow, dispute, safety/emergency, medical, legal, financial-sensitive, verification, moderation, voice, attachment, or administrative workflows.** FCM is an optional external transport for an already-created in-app notification, never the source of a high-stakes state transition.

## Current repository state

`FCM_SERVICE_ACCOUNT_JSON` is empty in `.env.example`; therefore the application truthfully returns `not_configured` for FCM transport while preserving in-app fallback. No client FCM SDK, VAPID key, Firebase service-account secret, consented aggregate-delivery integration, or production acceptance evidence is configured in this repository. The existing `test:communications-boundary` regression remains the implementation gate for owner binding, consent, fallback persistence, outbox privacy, stale-token cleanup, and no delivery/read-receipt fabrication.
