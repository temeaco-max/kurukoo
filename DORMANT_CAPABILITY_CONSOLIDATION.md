# Dormant Capability Consolidation

**Scope:** Existing Opportunity Engine, broad background scheduler, and bounded service/route scan on `integration/main-convergence-audit`.

## Completed canonical Opportunity Engine

The prior `opportunityEngine.ts` was dormant and unsafe to activate unchanged. It read profile rows directly, generated static daily rewards and regional market assertions, claimed local demand and nearby provider availability without source evidence, generated fixed offer language, directly attempted push delivery, had no source-level deduplication or expiry, and was not mounted through an authenticated route or an active workspace consumer.

It is now connected through existing authorities only:

| Responsibility | Canonical owner reused | Completed behavior |
|---|---|---|
| Source signal | `deferredRequestService.ts` | Owner-scoped, non-expired open intentions produce a continuation suggestion. |
| Sponsored placement | `adManager.ts` | Only an active campaign whose registered keyword matches an owner’s current request can be projected, with its required disclosure. |
| Persistence/history | Existing `proactive_opportunities` table | Adds backward-compatible source, idempotency, disclosure, and expiry fields; one source signal yields one owner-scoped record. |
| API authorization | Existing `notificationRoutes.ts` | Authenticated `/api/opportunities` read, act, and dismiss routes derive identity from the authenticated principal, never a phone query parameter. |
| User surface | Existing `/daily-picks` workspace section | Existing Daily Picks loader displays the canonical opportunity feed with disclosure, review, and dismissal controls. |
| Request continuation | Existing chat route and Economic Request/deferred lifecycle | CTAs only return the user to Web Chat; they do not confirm a provider, price, payment, availability, dispatch, or fulfilment. |

No new Opportunity engine, request lifecycle, provider model, recommendation feed, memory store, or external source adapter was created. The former static daily-reward, unsupported regional-market, generic-demand, static wholesale, and fabricated delivery/price content is no longer generated by this engine.

## Completed single-instance scheduler composition

`src/startup/backgroundServices.ts` is now a startup initializer. `src/services/backgroundWorkers.ts` is the single canonical in-process recurring schedule for the current deployment. This uses the existing timer model and SQL.js persistence; no Redis, queue, cron product, worker framework, or external infrastructure was added.

| Job | Canonical schedule owner | Safety boundary |
|---|---|---|
| Economic orchestration and eligible escrow pass | `backgroundWorkers` via `runOrchestrationPass()` | Existing idempotent lifecycle and escrow controls remain authoritative. |
| Deferred request re-check | `backgroundWorkers` via `processDueDeferred()` | Invites eligible providers through `providerCoordination`; records canonical matching only; never fabricates a quote, external delivery, or fulfilment. |
| Reminders, safety, living-memory maintenance, retention, trust score | `backgroundWorkers` | Existing service owners are scheduled once. |
| Communications outbox | `backgroundWorkers` via `dispatchDueCommunicationOutbox()` | Durable leases, consent suppression, provider receipts, and unconfigured transport truthfulness remain authoritative. |
| Provider-verification expiry | `backgroundWorkers` | Existing verification owner only. |
| Bounded agent re-entry | `backgroundWorkers`, only when `KURUKOO_AGENT_ENABLED=true` | Existing agent quotas, tools, and notification rules remain authoritative. |

The startup service no longer starts the synthetic contact-name synchronizer, an independent outbox interval, duplicate retention/escrow intervals, or a separate agent timer. The scheduler prevents overlapping executions of the same labelled task, so a slow interval or bootstrap run cannot duplicate provider invitations, agent actions, escrow work, notifications, or rewards.

`contactSyncService.ts` remains **dormant / unsafe**. Its existing behavior synthesizes names from phone prefixes. It is intentionally not activated and must not return to production startup without a consented, evidence-backed contact source.

## Explicit architecture confirmation

This work introduces **no** parallel Opportunity Engine, scheduler framework, memory system, intent architecture, provider/business model, Economic Request lifecycle, notification authority, or external infrastructure. It reuses canonical request, provider-coordination, advertising, notification, workspace, and background-worker authorities.

## Remaining external activation dependencies

The new feed can only surface data already supported by internal deferred intentions or disclosed active campaigns. Live inventory, merchant availability, provider presence, prices, external market data, payment execution, SMS/WhatsApp/USSD transport, and any external contact synchronization remain conditional on the separately documented evidence, consent, receipt, provider, and operational requirements.
