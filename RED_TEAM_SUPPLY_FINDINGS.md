# Red-Team Supply Registry Findings

**Scope:** Current Provider Supply Registry at commit `7b5b7c5` on `integration/main-convergence-audit`.
**Decision before fixes:** **NO-GO** for controlled Nigerian supply acquisition until the P0/P1 findings below are closed.

| Finding | Severity | Affected area | Exploit/path | Repository-solvable | Proposed fix |
|---|---|---|---|---|---|
| Admin lifecycle transition can directly set `verified` or `active` | P0 | `providerSupplyRegistryRouter.ts`, `providerSupplyRegistry.ts` | An authenticated admin can call the generic transition endpoint to move an imported record through `claim_requested → claimed → verification_pending → verified → active` without an approved claim, review evidence, current provider verification, or capability revalidation. | Yes | Remove generic privileged state mutation. Expose only policy-specific review, freshness, claim-review, and activation actions; make activation the only route that can create `active`, and require all gates at the moment of activation. |
| Registry `verified` lacks a required registry-review evidence record | P1 | `providerSupplyRegistry.ts` | Any transition to `verified` can be recorded with an empty evidence object and no reviewer or review reference. The state name can be confused with provider verification. | Yes | Add explicit review evidence, reviewer hash, review timestamp, freshness fields, and a separate `reviewed`/`registry_verified` meaning. Never expose it as provider verification. |
| No source-policy allowlist | P1 | `providerSupplyRegistry.ts` | Any authenticated admin can import arbitrary HTTP/HTTPS source URLs. The system validates URL syntax but not source approval, terms review, operator approval, country/source-type restrictions, or freshness window. | Yes | Add source-policy records and require an approved policy before import. Do not fetch or crawl URLs automatically. |
| No bounded import batch or batch provenance | P1 | Registry import route/service | Every request imports one record without a batch ID, payload/field limits beyond individual strings, country restriction, or controlled-import counters. | Yes | Add batch IDs, explicit record/field/payload limits, Nigeria-only pilot policy, and operator/batch provenance. |
| No freshness or stale-state model | P1 | `provider_supply_entities` | `source_retrieved_at` is stored but never evaluated. Old records can remain indistinguishable from current supply and cannot be revalidated or removed without destroying history. | Yes | Add freshness state, next review time, last review fields, stale/removed transitions, and bounded revalidation events. |
| No deterministic duplicate detection | P1 | Registry import | Exact or near-duplicate businesses can be imported repeatedly. No candidate table, signals, confidence, or operator decision exists. | Yes | Normalize name/domain/phone/address/geography, create possible-duplicate candidates, and require explicit merge/reject decisions. No automatic destructive merge. |
| Nigerian geography is stored as free text | P1 | Registry import | `state` and `lga` accept arbitrary values and aliases; no canonical Nigerian state/LGA representation exists and coordinates may be supplied without provenance. | Yes | Add controlled Nigerian state/LGA/locality normalization and geocoding provenance. Preserve address; never invent coordinates. |
| Field minimization is not enforced | P1 | Registry import | Arbitrary public phone, address, opening-hours, and JSON fields are accepted without rejecting private-person data, sensitive metadata, or unnecessary records. | Yes | Restrict fields, reject sensitive/private-person patterns, and treat phone as public-business-only with explicit source context. |
| Dashboard claims aggregate-only but exposes raw feedback and request IDs | P1 | `pilotObservability.ts`, `adminRoutes.ts`, `public/admin/pilot.html` | `/api/admin/pilot-dashboard` returns recent notes and the dashboard renders arbitrary user text plus raw coordination request IDs while advertising aggregate-only semantics. | Yes | Make ordinary dashboard aggregate-only; move incident review to a separate authenticated operator endpoint with explicit redaction and access policy. Pseudonymize handoff identifiers. |
| Ordinary-user public supply presentation is not yet implemented | P2 | Public/customer discovery | No public supply listing surface exists, so the system does not currently blur it with provider discovery, but it also cannot provide the intended truthful public-listing experience. | Yes | Add a clearly labelled public-supply projection only after publish/review/freshness policy exists; never route it into provider coordination. |
| No controlled invitation mechanism for unclaimed public listings | P2 | Claim/acquisition workflow | Claim requests exist, but no operator-controlled invite/claim URL/QR workflow exists; no automatic outreach is correctly performed. | Yes | Add a manual operator invitation record or claim URL/QR mechanism with consent and expiry, without sending external messages automatically. |

## P0/P1 closure criteria

A controlled Nigerian pilot remains blocked until generic lifecycle mutation is removed, registry review and provider verification are separate, source policy and bounded import checks exist, freshness and duplicate/geography safeguards are present, field minimization is enforced, and the pilot dashboard no longer exposes raw notes or raw request identifiers under aggregate-only semantics.
